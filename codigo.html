Sección 4

Generación de código intermedio y final

Entre el árbol que entiende el front-end y las instrucciones que entiende el procesador hay un paso intermedio deliberado. Esta sección explica por qué existe, qué formas toma y cómo se llega desde ahí al código máquina.

Código intermedio: un lenguaje para una máquina que no existe

El código intermedio (o representación intermedia, IR) es una versión del programa más simple que el código fuente y más abstracta que el código máquina. Se parece a un ensamblador para una máquina idealizada: con tantos registros como se necesiten, sin peculiaridades de ningún procesador real.

Un compilador podría traducir directamente del árbol sintáctico al código máquina. Pasar por una representación intermedia es una decisión de diseño que aporta tres ventajas:

  • Portabilidad. El mismo front-end sirve para cualquier máquina: solo cambia el back-end. Es el esquema N + M descrito en Estructura.
  • Optimización. La mayoría de las mejoras (eliminar cálculos repetidos, simplificar expresiones, reorganizar bucles) se razonan mejor sobre instrucciones simples y uniformes que sobre un árbol o sobre código máquina lleno de detalles.
  • Reutilización. Herramientas de análisis, depuración y verificación pueden trabajar sobre la IR sin conocer ni el lenguaje fuente ni el procesador.

Código de tres direcciones

Es la forma más usada en los libros de texto y la base de muchas IR reales. Cada instrucción tiene a lo sumo un operador y tres "direcciones" (dos operandos y un resultado), y los resultados parciales se guardan en variables temporales t1, t2, … que el compilador inventa:

Fuente

total = precio * cantidad + 5

Tres direcciones

t1 = precio * cantidad
t2 = t1 + 5
total = t2

Las instrucciones de tres direcciones se almacenan en memoria como cuádruplas (operador, operando 1, operando 2, resultado) o como triples, que ahorran el campo de resultado refiriéndose a la posición de la instrucción. El flujo de control se expresa con etiquetas y saltos condicionales, igual que en un ensamblador:

      // if (a < b) max = b; else max = a;
      if a < b goto L1
      max = a
      goto L2
L1:   max = b
L2:   …

El mismo cálculo en LLVM IR

LLVM IR es una IR tipada en forma SSA: cada %nombre recibe un valor una sola vez. Clang, rustc y swiftc generan este código.

%1 = mul i32 %precio, %cantidad
%2 = add i32 %1, 5
store i32 %2, ptr %total

El mismo cálculo en CIL (.NET)

CIL es un bytecode de pila. El compilador de C# lo guarda dentro del ensamblado .dll junto con metadatos que describen los tipos.

ldloc.0      // apila precio
ldloc.1      // apila cantidad
mul          // precio * cantidad
ldc.i4.5     // apila 5
add
stloc.2      // guarda en total

Código final: hablar el idioma del procesador

La generación de código final (o código objeto) es la última fase del compilador. Toma el código intermedio, ya optimizado, y produce instrucciones para una arquitectura concreta. Es la fase más dependiente de la máquina, y resuelve tres problemas:

  1. Selección de instrucciones. Elegir qué instrucción (o secuencia) del procesador realiza cada operación intermedia. Un t1 = a * 2 puede convertirse en una multiplicación, en un desplazamiento de bits o en una suma a + a, según cuál sea más barata.
  2. Asignación de registros. El procesador tiene pocos registros (16 de propósito general en x86-64) y son mucho más rápidos que la memoria. Hay que decidir qué variables y temporales viven en registros en cada momento, y cuáles se "derraman" a memoria. Es un problema de coloreo de grafos.
  3. Planificación de instrucciones. Ordenar las instrucciones para aprovechar la segmentación y el paralelismo interno del procesador sin alterar el resultado.

Tres direcciones (optimizado)

t1 = precio * cantidad
total = t1 + 5

Ensamblador x86-64 (sintaxis Intel)

mov   eax, DWORD PTR [precio]
imul  eax, DWORD PTR [cantidad]
add   eax, 5
mov   DWORD PTR [total], eax

El texto en ensamblador pasa después por el ensamblador, que lo convierte en bytes, y por el enlazador, que une los distintos archivos objeto y bibliotecas en un ejecutable.

¿Cuándo se genera el código final? AOT y JIT

Antes de ejecutar (AOT)

C, C++, Rust y Go producen el código máquina en el momento de compilar. El ejecutable ya contiene instrucciones nativas; el usuario no necesita el compilador ni una máquina virtual.

Justo a tiempo (JIT)

Java y .NET entregan código intermedio (bytecode, CIL). Cuando el programa se ejecuta, un compilador JIT dentro de la máquina virtual traduce cada método a código nativo la primera vez que se llama y guarda el resultado. Así el mismo archivo corre en cualquier arquitectura que tenga la máquina virtual, y el JIT puede optimizar con información que solo existe en ejecución.

Ejemplo con .NET: cuando se compila un proyecto de C#, Roslyn genera CIL y metadatos dentro de un ensamblado. Al ejecutarlo, el CLR verifica que el CIL sea seguro en cuanto a tipos y el compilador JIT (RyuJIT) lo convierte a código nativo por método, bajo demanda. .NET también ofrece compilación AOT (ReadyToRun y Native AOT) para evitar ese trabajo en tiempo de ejecución. La fase de "generación de código final" existe en ambos casos; lo que cambia es el momento en que ocurre.

Resumen de la sección

  • El código intermedio es la frontera entre front-end y back-end: independiente de la máquina, simple y pensado para optimizar.
  • Las formas más comunes son el código de tres direcciones (y su variante SSA) y los bytecodes de pila como JVM y CIL.
  • El código final es el código máquina de una arquitectura concreta; generarlo implica seleccionar instrucciones, asignar registros y planificar su orden.
  • El código final puede producirse antes de ejecutar (AOT) o durante la ejecución (JIT); la fase es la misma, cambia el momento.
